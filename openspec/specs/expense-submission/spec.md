## Requirements
### Requirement: Expense Creation Endpoint
The `Api` layer SHALL expose `POST /api/expenses`, restricted to the `Employee` and `Manager`
roles (`docs/SDS.md` §5.2, `docs/FRS.md` §4.1.5), accepting `expenseDate`, `category`, `amount`,
`currency`, `description`, `receiptAttachmentId`, and `action` (`Draft` or `Submit`). On success
it SHALL create an `Expense` row owned by the authenticated employee with `Status` set to
`Draft` or `Submitted` per `action`, and return `201 Created` with the created expense
(`docs/FRS.md` §4.1.2).

#### Scenario: Draft creation succeeds
- **WHEN** an authenticated Employee or Manager POSTs a valid request with `action: "Draft"`
- **THEN** the response is `201 Created`, an `Expense` row exists with `Status = Draft`, and
  `SubmittedAt` is null

#### Scenario: Immediate-submit creation succeeds
- **WHEN** an authenticated Employee or Manager POSTs a valid request with `action: "Submit"`
  and all validations pass
- **THEN** the response is `201 Created`, the `Expense` row has `Status = Submitted`, and
  `SubmittedAt` is populated

#### Scenario: Unauthenticated request is rejected
- **WHEN** a request to `POST /api/expenses` carries no valid `Authorization: Bearer` token
- **THEN** the response is `401` with code `AUTHENTICATION_FAILED`

#### Scenario: Role outside Employee/Manager is rejected
- **WHEN** an authenticated user whose derived role is `Finance` or `ComplianceOfficer` POSTs to
  `/api/expenses`
- **THEN** the response is `403` with code `AUTHORIZATION_FAILED`

### Requirement: Expense Number Generation
The system SHALL generate an immutable, globally unique `ExpenseNumber` at creation time in
format `EXP-yyyyMMdd-XXXX` (**BR-09**, `docs/SDS.md` §3.9), where `yyyyMMdd` is the company-local
date the expense record was created (`CreatedAt`), and `XXXX` is a zero-padded, globally
increasing sequence generated by a concurrency-safe mechanism (logged as an ADR in
`docs/decisions/`, since `docs/SDS.md` §3.9 specifies the format but not the generation
mechanism). The client SHALL NOT supply or influence `ExpenseNumber`.

#### Scenario: Expense number reflects the creation date, not the expense date
- **WHEN** an expense with `ExpenseDate` `2026-01-05` is created on `2026-07-21`
- **THEN** the generated `ExpenseNumber` begins with `EXP-20260721`

#### Scenario: Concurrent creation never collides
- **WHEN** two `POST /api/expenses` requests are submitted concurrently on the same company-local
  day
- **THEN** each succeeds with a distinct `ExpenseNumber`, and neither caller sees a database
  constraint-violation error

#### Scenario: Client-supplied expense number is ignored
- **WHEN** a `POST /api/expenses` request body includes an `expenseNumber` field
- **THEN** the server-generated value is used regardless, and the client-supplied value has no
  effect on the created `Expense` row

### Requirement: Field-Level Validation
The `Application` layer SHALL reject, identically for `Draft` and `Submitted`, any request whose
`Category` is not one of the seven `ExpenseCategory` values, whose `Currency` is not exactly
`INR` (`docs/FRS.md` §4.1.1 — no multi-currency support is in scope), or whose `Description`
exceeds 500 characters (`docs/FRS.md` §4.1.1), with `400 VALIDATION_ERROR` and field-level
`fields` detail. No `Expense` row SHALL be created on failure.

#### Scenario: Invalid category is rejected
- **WHEN** a request's `category` is not one of the seven defined `ExpenseCategory` values
- **THEN** the response is `400` with code `VALIDATION_ERROR` and a `fields` entry for `category`

#### Scenario: Non-INR currency is rejected
- **WHEN** a request's `currency` is anything other than `INR`
- **THEN** the response is `400` with code `VALIDATION_ERROR` and a `fields` entry for `currency`

#### Scenario: Description over 500 characters is rejected
- **WHEN** a request's `description` exceeds 500 characters
- **THEN** the response is `400` with code `VALIDATION_ERROR` and a `fields` entry for
  `description`

### Requirement: Business Rule Validation
The `Application` layer SHALL reject, identically for `Draft` and `Submitted` (a Draft is not a
relaxed-validation state), any request where `Amount` is not greater than zero (**BR-01**), or
`ExpenseDate` is after the current company-local date (**BR-02**, **BR-10**), with
`422 BUSINESS_RULE_VIOLATION` and field-level detail. No `Expense` row SHALL be created on
failure.

#### Scenario: Zero or negative amount is rejected on Draft
- **WHEN** a request with `action: "Draft"` has `amount <= 0`
- **THEN** the response is `422` with code `BUSINESS_RULE_VIOLATION`, and no `Expense` row is
  created

#### Scenario: Zero or negative amount is rejected on Submit
- **WHEN** a request with `action: "Submit"` has `amount <= 0`
- **THEN** the response is `422` with code `BUSINESS_RULE_VIOLATION`, and no `Expense` row is
  created

#### Scenario: Future expense date is rejected on Draft
- **WHEN** a request with `action: "Draft"` has `expenseDate` after the current company-local
  date
- **THEN** the response is `422` with code `BUSINESS_RULE_VIOLATION`, and no `Expense` row is
  created

#### Scenario: Future expense date is rejected on Submit
- **WHEN** a request with `action: "Submit"` has `expenseDate` after the current company-local
  date
- **THEN** the response is `422` with code `BUSINESS_RULE_VIOLATION`, and no `Expense` row is
  created

### Requirement: Attachment Linkage and Ownership Validation
The `Application` layer SHALL require `receiptAttachmentId` to reference an existing `Attachment`
that is not already linked to another `Expense` and whose `UploadedByEmployeeId` matches the
authenticated caller (**BR-03**, `docs/FRS.md` §4.1.1), rejecting any violation with
`422 BUSINESS_RULE_VIOLATION` rather than a raw database constraint error. No `Expense` row SHALL
be created on failure.

#### Scenario: Missing attachment is rejected
- **WHEN** `receiptAttachmentId` does not reference any existing `Attachment`
- **THEN** the response is `422` with code `BUSINESS_RULE_VIOLATION`

#### Scenario: Already-linked attachment is rejected
- **WHEN** `receiptAttachmentId` references an `Attachment` already linked to a different
  `Expense`
- **THEN** the response is `422` with code `BUSINESS_RULE_VIOLATION`

#### Scenario: Attachment uploaded by a different employee is rejected
- **WHEN** `receiptAttachmentId` references an `Attachment` whose `UploadedByEmployeeId` does not
  match the authenticated caller's employee ID
- **THEN** the response is `422` with code `BUSINESS_RULE_VIOLATION`

### Requirement: Submit Existing Draft Endpoint
The `Api` layer SHALL expose `POST /api/expenses/{id}/submit`, restricted to the expense's owning
employee (`docs/SDS.md` §5.2), transitioning a `Draft` expense to `Submitted` after re-running
the same field-level and business-rule validation as creation, and setting `SubmittedAt`.

#### Scenario: Owner submits their own Draft
- **WHEN** the owning employee POSTs to `/api/expenses/{id}/submit` for their own `Draft` expense
  that passes all validation
- **THEN** the response is `200`, the expense's `Status` becomes `Submitted`, and `SubmittedAt`
  is populated

#### Scenario: Non-owner is rejected
- **WHEN** an employee who does not own the expense POSTs to `/api/expenses/{id}/submit`
- **THEN** the response is `403` with code `AUTHORIZATION_FAILED`

#### Scenario: Submitting a non-Draft expense is rejected
- **WHEN** `POST /api/expenses/{id}/submit` targets an expense whose `Status` is not `Draft`
- **THEN** the response is `422` with code `BUSINESS_RULE_VIOLATION`, and the expense's `Status`
  is unchanged

#### Scenario: Re-validation blocks submission of an invalid Draft
- **WHEN** `POST /api/expenses/{id}/submit` targets a `Draft` expense whose stored data no
  longer passes field-level or business-rule validation (e.g. its linked attachment was removed)
- **THEN** the response is `422` with code `BUSINESS_RULE_VIOLATION`, and the expense's `Status`
  remains `Draft`

### Requirement: Workflow Initialization and Audit Fields
On successful creation or submission, the system SHALL set `CreatedAt`/`UpdatedAt`
automatically; whenever `Status` becomes `Submitted` (via `action: "Submit"` at creation or via
the submit endpoint), `SubmittedAt` SHALL be set to the current timestamp. `ApprovedAt`,
`ComplianceApprovedAt`, `RejectedAt`, `ReimbursedAt`, and their `...ByEmployeeId` fields SHALL
remain null. No audit field is client-writable via any request field (`docs/SDS.md` §6.8).

#### Scenario: Draft has no SubmittedAt
- **WHEN** an expense is created with `action: "Draft"`
- **THEN** `SubmittedAt` is null and all later-workflow audit fields are null

#### Scenario: Submitted expense has SubmittedAt populated
- **WHEN** an expense's `Status` becomes `Submitted`, whether at creation or via the submit
  endpoint
- **THEN** `SubmittedAt` is set to the current timestamp

#### Scenario: Client cannot set audit fields directly
- **WHEN** a `POST /api/expenses` or `POST /api/expenses/{id}/submit` request body includes any
  of `submittedAt`, `approvedAt`, `rejectedAt`, `reimbursedAt`, or their `...ByEmployeeId`
  counterparts
- **THEN** those values are ignored, and the system-computed values are used instead
