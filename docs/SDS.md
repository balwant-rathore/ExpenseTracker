# Software Design Specification (SDS)

## Expense Management App

This document is the source of technical truth. Every `/plan` must conform to the schema, API contracts, and architecture decisions below. Changes to this document are architecture decisions and should be logged in `docs/decisions/` using Architecture Decision Records (ADRs).

## 1. Architecture Overview

The application shall be implemented as a pnpm monorepo consisting of two workspaces.

```
frontend/    → React 19 Single Page Application (SPA)
backend/     → ASP.NET Core 9 Web API
```
### 1.1 High-Level Architecture

```
┌────────────────────────────┐
│        React Frontend      │
│  TanStack Query + Zustand  │
└──────────────┬─────────────┘
               │ HTTPS (REST/JSON)
               ▼
┌────────────────────────────┐
│ ASP.NET Core 9 Web API     │
│ JWT Authentication         │
│ Authorization              │
│ Validation                 │
│ Business Logic             │
└──────────────┬─────────────┘
               │ EF Core
               ▼
┌────────────────────────────┐
│ Microsoft SQL Server 2022  │
│ Expense Management Schema  │
└────────────────────────────┘
```

### 1.2 Request Flow

```
React SPA
      │
      ▼
TanStack Query
      │
REST API (HTTPS)
      │
Authentication & Authorization
      │
Controllers
      │
Application Services
      │
Entity Framework Core
      │
SQL Server
```

### 1.3 Architectural Decisions

| Area | Architectural Decision |
|------|--------------------------|
| Client-Server Communication | Frontend communicates exclusively with the backend through REST APIs. |
| Business Logic | Backend is the single source of truth for all business rules. |
| Data Access | Entity Framework Core is the only data access mechanism. |
| Database Schema | Database changes are managed exclusively through EF Core migrations. |
| Authentication | JWT access tokens with server-side persisted refresh tokens. |
| Authorization | Role-based authorization enforced entirely by the backend. |
| Workflow | All expense workflow transitions are validated by the backend. |
| Validation | Client-side validation improves UX; server-side validation is authoritative. |
| Business Rules | Every business rule defined in the FRS shall be enforced by the backend. |

### 1.4 Infrastructure Decisions

| Area | Architectural Decision |
|------|--------------------------|
| File Storage | Receipt files are stored on the server filesystem. |
| Attachment Metadata | Database stores only attachment metadata and relative storage path. |
| Report Generation | Reports are generated by the backend from SQL Server data. |
| Report Format | Reports are exported as Microsoft Excel (.xlsx) files. |
| Email Notifications | No SMTP integration is implemented. |
| Notification Output | Notifications are written to an HTML log containing To, CC, Subject, Body and Timestamp. |
| Password Reset | OTPs are generated for development and logged to the server console as defined in the FRS. |
| Cross-Origin Requests | A named CORS policy (`Api.Cors.CorsPolicyNames.Frontend`) allows only origins listed in `Cors:AllowedOrigins` configuration (empty/deny-all by default; per-environment allow-list). See `docs/decisions/ADR-0019-backend-cors-policy.md`. |

### 1.5 Architectural Assumptions

| Area | Decision |
|------|----------|
| Employee Master Data | Employee table is created and seeded during application setup. |
| Employee Management | Employee records are not managed by the application after setup. |
| Reporting Hierarchy | Every employee reports to exactly one manager. |
| Expense Ownership | Every expense belongs to exactly one employee. |
| Receipt Attachment | Every expense contains exactly one receipt attachment. |
| Compliance | A single Compliance Officer role exists in the system. |
| Reimbursement | Payment is performed by an external accounting/payroll system; the application tracks reimbursement status only. |

## 4. Authentication Design

### 4.1 Authentication Model

- Token-based authentication using JWT access tokens and refresh tokens.
- Authentication and authorization are enforced entirely by the backend.
- Roles are resolved from the Employee record on every authenticated request.
- Supported roles:
  - Employee
  - Manager
  - Finance
  - Compliance Officer

### 4.2 Credentials

- Passwords are hashed using BCrypt before persistence.
- Passwords are never stored or logged in plaintext.
- Password policy:
  - Minimum 8 characters
  - At least one alphabetic character
  - At least one numeric digit

### 4.3 Access Token

| Property | Value |
|----------|-------|
| Format | JWT |
| Algorithm | HS256 |
| Lifetime | 15 minutes |
| Claims | `sub` (UserId) only |

- No employee information or permissions are embedded in the token.

### 4.4 Refresh Token

| Property | Value |
|----------|-------|
| Format | Cryptographically secure random token |
| Lifetime | 7 days |
| Storage | SHA-256 hash only |

- Refresh tokens are rotated on every successful refresh.
- Reuse of a revoked refresh token invalidates all active refresh tokens for the user.

### 4.5 Password Reset

- Uses a 6-digit numeric OTP.
- OTP is stored as a SHA-256 hash.
- OTP expires after 10 minutes.
- OTP is single-use.
- Previous unused OTPs are invalidated when a new OTP is generated.
- OTPs are logged to the application console; no email service is used.

### 4.6 Authentication Middleware

Protected endpoints require a valid JWT access token.

The authentication middleware:

- Validates the JWT.
- Resolves the authenticated user.
- Loads the associated Employee record.
- Determines the user's role.
- Populates the request context with the authenticated identity.

### 4.7 Rate Limiting

Rate limiting is applied to:

- `POST /api/auth/register`
- `POST /api/auth/login`
- `POST /api/auth/forgot-password`
- `POST /api/auth/reset-password`

Requests exceeding configured limits return:

```
HTTP 429 Too Many Requests
```

### 4.8 Security Principles

- Authentication errors shall not reveal sensitive information.
- Registration and password reset shall prevent account enumeration.
- Password reset revokes all active refresh tokens.
- Authorization is enforced exclusively by the backend.
- JWT signing keys and other secrets are supplied through environment-specific configuration.

- Base Path: `/api`

- Error responses follow Section 9

## 6. Expense Workflow Design

The Expense Management workflow defines the valid lifecycle of an expense from creation through reimbursement. All workflow transitions shall be enforced by the backend. Clients shall not directly modify expense status.

The workflow described in this section implements the business rules defined in the FRS.

### 6.1 Expense Lifecycle

The application supports two workflow paths.

#### Standard Workflow

Applicable to all expense categories except **Client Entertainment**.

```text
Draft
   │
   ▼
Submitted
   ├──────────────►Cancelled
   ├──────────────► Rejected
   │
   ▼
Approved
   │
   ▼
Reimbursed
```

#### Client Entertainment Workflow

Applicable only to the **Client Entertainment** expense category.

```text
Draft
   │
   ▼
Submitted
   ├──────────────► Cancelled
   ├──────────────► Rejected
   │
   ▼
Approved
   │
   ▼
Compliance Approved
   │
   ├──────────────► Rejected
   │
   ▼
Reimbursed
```

### 6.2 Supported Expense States

| Status | Description |
|---------|-------------|
| Draft | Expense has been saved but not submitted for approval. |
| Submitted | Expense has been submitted and is awaiting manager review. |
| Approved | Expense approved by the reporting manager. |
| Compliance Approved | Client Entertainment expense approved by the Compliance Officer. |
| Rejected | Expense rejected by either the Manager or Compliance Officer. |
| Reimbursed | Expense reimbursement has been completed by Finance. |
| Cancelled | Expense cancelled by Employee. |

### 6.3 State Transition Matrix

| Current State | Action | Performed By | Next State |
|---------------|--------|--------------|------------|
| Draft | Save Draft | Employee / Manager | Draft |
| Draft | Submit | Employee / Manager | Submitted |
| Submitted | Approve | Manager | Approved |
| Submitted | Reject | Manager | Rejected |
| Submitted | Cancel | Expense Owner | Cancelled* |
| Approved | Compliance Approve | Compliance Officer | Compliance Approved |
| Approved | Compliance Reject | Compliance Officer | Rejected |
| Approved | Reimburse (Non-Client Entertainment) | Finance | Reimbursed |
| Compliance Approved | Reimburse | Finance | Reimbursed |

\*Applicable only when cancellation is permitted by the FRS.
\*\* Expenses may be edited only while in Draft or Submitted state.

### 6.4 Authorization Matrix

| Operation | Employee | Manager | Finance | Compliance Officer |
|-----------|:--------:|:-------:|:-------:|:------------------:|
| Create Expense | ✓ | ✓ | ✗ | ✗ |
| Save Draft | ✓ | ✓ | ✗ | ✗ |
| Submit Expense | ✓ | ✓ | ✗ | ✗ |
| Edit Own Draft or Submitted Expense | ✓ | ✓ | ✗ | ✗ |
| Cancel Own Draft or Submitted Expense | ✓ | ✓ | ✗ | ✗ |
| View Own Expenses | ✓ | ✓ | ✗ | ✗ |
| View Team Expenses | ✗ | ✓ | ✗ | ✗ |
| View Organization Expenses | ✗ | ✗ | ✓ | ✗ |
| View Approved Client Entertainment Expenses | ✗ | ✗ | ✗ | ✓ |
| Manager Approval | ✗ | ✓ | ✗ | ✗ |
| Compliance Approval | ✗ | ✗ | ✗ | ✓ |
| Compliance Rejection | ✗ | ✗ | ✗ | ✓ |
| Reimburse Expense | ✗ | ✗ | ✓ | ✗ |
| Export Monthly Report | ✗ | ✗ | ✓ | ✗ |

### 6.8 Audit Information

The application shall maintain audit information for workflow transitions.

The following fields shall be populated automatically during state transitions.

| Workflow State | Audit Fields Updated |
|----------------|---------------------|
| Submitted | SubmittedAt |
| Approved | ApprovedAt, ApprovedByEmployeeId |
| Compliance Approved | ComplianceApprovedAt, ComplianceApprovedByEmployeeId |
| Rejected | RejectedAt, RejectedByEmployeeId, RejectionComment,  |
| Reimbursed | ReimbursedAt, ReimbursedByEmployeeId |

Audit fields shall never be editable through any public API.

## 7. Notification Design

Notifications are generated for expense workflow events defined in the FRS.

- Email delivery is out of scope.
- Notifications are written to a configurable HTML log file.
- Notifications are generated only after a successful transaction commit.

### 7.1 Notification Matrix

| Event | Trigger | To | CC | Template |
|--------|---------|----|----|----------|
| Expense Submitted | Status → Submitted | Employee | Reporting Manager | Submitted |
| Expense Approved | Status → Approved | Employee | Reporting Manager, Finance | Approved |
| Expense Rejected | Status → Rejected | Employee | — | Rejected |
| Expense Reimbursed | Status → Reimbursed | Employee | Reporting Manager, Finance | Reimbursed |

Recipient email addresses are resolved from the `Employee` table.

### 7.2 Notification Service

**Responsibilities**

- Resolve recipients
- Generate notification subject and HTML body
- Append notification to the HTML log
- Record notification timestamp

The service contains no workflow or authorization logic.

### 7.3 Processing Flow

```text
Workflow Action
      │
      ▼
Business Validation
      │
      ▼
Database Transaction
      │
      ▼
Commit
      │
      ▼
Notification Service
      │
      ▼
Append HTML Notification
```

Notifications are not generated if the transaction is rolled back.

### 7.4 Notification Log

| Property | Value |
|----------|-------|
| Format | HTML |
| Location | Configurable application directory |
| File | Created automatically if missing |
| Write Mode | Append |

Each notification entry contains:

- Timestamp
- Event
- To
- CC
- Subject
- HTML Body

### 7.5 Notification Templates

| Event | Template Data |
|--------|---------------|
| Submitted | Expense Number, Employee, Category, Amount, Submission Date |
| Approved | Expense Number, Employee, Category, Approved By, Approval Date |
| Rejected | Expense Number, Employee, Rejection Comment, Rejected By, Rejection Date |
| Reimbursed | Expense Number, Employee, Amount, Reimbursement Date |

Templates shall not expose internal identifiers or confidential information.

### 7.6 Notification Runtime Behavior

| Area | Design |
|------|--------|
| Failure Handling | Notification failures do not roll back committed workflow transactions. |
| Logging | Notification failures are logged using the application logging framework. |
| Client Response | Workflow API returns its original success response regardless of notification outcome. |
| Recovery | Notification failures do not affect subsequent notifications. |

### 7.7 Notification Configuration

| Setting | Purpose |
|---------|---------|
| `NotificationLogDirectory` | HTML log directory |
| `NotificationLogFileName` | HTML log file name |
| `NotificationTimestampFormat` | Timestamp format |

## 9. Error Handling

All non-success responses use the standard error contract.

```json
{
  "error": {
    "code": "ERROR_CODE",
    "message": "Description",
    "fields": [],
    "traceId": "..."
  }
}
```

`fields` is included only for validation errors.

### 9.1 Error Matrix

| HTTP | Error Code | Usage |
|------|------------|-------|
| 400 | `VALIDATION_ERROR` | Request validation failed |
| 401 | `AUTHENTICATION_FAILED` | Invalid or expired credentials/token |
| 403 | `AUTHORIZATION_FAILED` | Insufficient permissions |
| 404 | `RESOURCE_NOT_FOUND` | Resource does not exist or is inaccessible |
| 409 | `RESOURCE_CONFLICT` | Duplicate or conflicting resource |
| 410 | `RESOURCE_EXPIRED` | Expired one-time resource (OTP) |
| 422 | `BUSINESS_RULE_VIOLATION` | Business rule violation |
| 429 | `RATE_LIMIT_EXCEEDED` | Rate limit exceeded |
| 500 | `INTERNAL_SERVER_ERROR` | Unexpected server error |

### 9.2 Exception Handling

A global exception handler shall:

- Catch unhandled exceptions.
- Log exception details.
- Map exceptions to the appropriate HTTP response.
- Return the standard error contract with a `traceId`.

Controllers and services shall not implement duplicate exception handling.

### 9.3 Logging

Unexpected errors shall log:

- Timestamp
- TraceId
- Exception Type
- Exception Message
- Stack Trace
- HTTP Method
- Request Path
- Authenticated UserId (if available)

Sensitive information shall never be logged:

- Passwords
- Password hashes
- JWT access tokens
- Refresh tokens
- Password reset OTPs

### 9.4 Design Rules

- Validation executes before business logic.
- Authentication and authorization errors shall not reveal sensitive information.
- Business rule violations remain distinct from validation errors.
- Internal implementation details shall never be returned to clients.
- All APIs return a consistent error response format.

## 10. Testing Strategy

Automated tests verify FRS requirements, business rules, API contracts, security, workflow transitions and regression prevention. Every FRS requirement shall be traceable to one or more automated tests.

### 10.1 Test Matrix

| Level | Technology | Scope |
|------|------------|-------|
| Unit | xUnit | Business logic, validators, utilities |
| Integration | xUnit + WebApplicationFactory | APIs, middleware, EF Core, SQL Server, file storage, notifications |
| Component | Vitest + React Testing Library | React components and UI interactions |
| End-to-End | Playwright | Complete user workflows |

### 10.2 Functional Coverage

| Area | Coverage |
|------|----------|
| Authentication | Registration, Login, Logout, Refresh Token, Password Reset |
| Expense Workflow | Draft, Submit, Approve, Reject, Compliance, Reimburse |
| Business Rules | FRS business rule validation |
| API Contracts | Request validation, responses, status codes, authorization |
| Dashboard & Reports | Dashboard metrics, Finance search, Excel export |
| File Upload | Validation, storage, retrieval |
| Notifications | Event generation, recipients, HTML log |

### 10.3 Test Data

- Tests use isolated, repeatable test data.
- Test databases are recreated using EF Core migrations.
- Required Employee seed data is initialized before execution.

### 10.4 Coverage Requirements

| Requirement | Coverage |
|------------|----------|
| Public APIs | Integration tests |
| Workflow transitions | Automated tests |
| Business rules | Dedicated test cases |
| FRS requirements | Traceable automated tests |
| Defect fixes | Regression test required |

### 10.5 Testing Principles

- Tests are deterministic and independent.
- Tests verify observable behavior rather than implementation details.
- Business rules are tested once at the backend; frontend tests do not duplicate them.
- Automated tests execute as part of the CI pipeline.

## 11. Cross-Cutting Conventions

### 11.1 Design Matrix

| Area | Convention |
|------|------------|
| API | RESTful, stateless, `/api` base path, JSON by default |
| Validation | Client-side for usability; backend remains authoritative |
| Authorization | Enforced exclusively by the backend |
| Transactions | State-changing operations execute within database transactions; post-processing (e.g., notifications) occurs after commit |
| Audit | `CreatedAt` and `UpdatedAt` managed automatically; workflow audit fields are system-managed |
| Time | Company local timezone used consistently across the application |
| File Storage | Files stored on the server filesystem; only metadata persisted in the database |
| Configuration | Environment-specific configuration; secrets stored outside source control |
| Dependency Injection | ASP.NET Core DI with abstraction-based dependencies |
| Database | Schema managed exclusively through EF Core migrations |
| Performance | Database-side filtering, sorting and pagination; use indexes where appropriate; stream large exports |
| Source Control | Git; exclude build outputs, uploads, logs and secrets |

### 11.2 Naming Conventions

| Area | Convention |
|------|------------|
| Database | PascalCase entities, `<EntityName>Id` keys |
| C# | PascalCase types/members, `I*` interfaces, `_camelCase` private fields |
| TypeScript | PascalCase components/types, `camelCase` functions/variables, `use*` hooks, `UPPER_SNAKE_CASE` constants |

### 11.3 Coding Standards

| Area | Convention |
|------|------------|
| Class | One public class per file |
| Service | Single responsibility |
| Dependencies | Constructor injection only |
| Async | `async/await` + `CancellationToken` |
| Controllers | No business logic |
| Nullable | Enabled |
| Implicit Usings | Enabled |
| Formatting | EditorConfig enforced |

### 11.3 Documentation

| Artifact | Purpose |
|---------|---------|
| FRS | Functional requirements |
| SDS | Technical design |
| ADR | Architecture decisions |
| OpenAPI / Swagger | API specification |
| EF Core Migrations | Database versioning |
| Automated Tests | Requirement verification |

### 11.4 Design Principles

- Separation of Concerns
- Single Responsibility Principle (SRP)
- RESTful architecture
- Defense in Depth
- Convention over Configuration
- Consistent error handling
- End-to-end traceability between FRS, implementation and tests
